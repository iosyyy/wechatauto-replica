## 方案比较

| 方案 | 取舍 |
| --- | --- |
| 保留 Windows，增加 Linux 后端 | 采用。复用解析与数据库算法，隔离系统相关代码，便于同步上游。 |
| 直接改成 Linux 专用库 | 不采用。破坏现有 Windows 使用方式，也增加后续合并成本。 |
| 在 Wine 中运行现有库 | 不采用。没有当前版本的完整成功验证，UIA 和 Windows OCR 仍是阻碍。 |

## 必须明确的运行边界

这不是无客户端的微信协议服务。实际在线收发仍需要官方 Linux 微信登录并常驻；
发送还需要可用的图形会话。数据库解析不需要启动 GUI 自动化模块。
初期目标是 Linux x86_64、官方微信 4.x；其它架构或客户端版本不自动视为兼容。

## 阶段一：跨平台读取基础

1. 包的公开名称延迟导入，读取数据库不加载 Windows GUI。
2. `pywin32`、`winsdk`、`uiautomation` 仅在 Windows 安装。
3. 保留上游 SQLCipher 页校验、WAL 合并、分库查询、成员映射和监听逻辑。
4. Linux 使用独立的账号发现与密钥加载后端，支持显式账号和私有密钥文件。
5. 仅接受通过目标数据库第一页 HMAC 验证的密钥；支持主密钥派生与逐库密钥。
6. Linux 不沿用 Windows 的自动切换账号逻辑：多账号必须显式选择，失败不得
   静默改用另一个账号；缺少或错误密钥必须给出明确失败。
7. Linux 密钥缓存权限为目录 `0700`、文件 `0600`，不得打印密钥内容。

这个阶段交付可用的导入、账号发现、已提供密钥下的解密与读取，不把自动取钥
或真实微信客户端验证标记为已完成。

## 阶段二：真实客户端取钥与文本发送

- 先在测试账号和固定 Linux 客户端版本验证密钥来源、真实表结构与 WAL。
- 不复制 Windows 的 DLL 偏移。自动取钥必须独立适配 Linux 进程，并通过数据库
  HMAC 验证；权限不足时报告失败，不自动关闭系统进程隔离策略。
- 优先使用 Linux 无障碍接口。定位不可靠时停止发送；不能用猜测的像素位置
  静默发到当前会话。
- 发送目标以账号与会话 username 绑定，昵称仅用于搜索，并检查重名与实际目标。
- 输入框校验后只提交一次；结果不明时记录未确认，由数据库回读核实，不能盲目重发。
- 图片、语音、朋友圈互动不在首次文本收发验收范围。

## 阶段三：LangBot 桥接

Linux 微信 → 本地数据库 → 持久收件箱 → LangBot → 持久发件箱 → Linux GUI。

- 接收事件先持久化再确认监听进度，网络重试不依赖内存队列。
- 上游监听器重试耗尽后会推进水位，因此不能直接把远程 HTTP 请求作为唯一回调。
- 持久化失败时暂停读取；不能让监听器丢弃后继续推进水位。
- 消息按账号、会话、分库和本地消息编号去重，保留真实发送者与时间。
- 群总结可以读取允许群的历史；自动回复只消费启用后的新消息。
- 排除机器人自己的消息；限制可读可写会话。桥接接口使用认证并限制监听地址。
- 既有 LangBot 模型、人格、插件与记忆配置继续使用；切换路由前先完成真实验收。

## 验证与当前部署约束

- 导入测试在没有 Windows 依赖的 Python 中运行。
- 构造真实 SQLite 文件，按上游页格式加密后验证密钥、解密、查询、监听、
  错误密钥、重名账号、权限和路径边界；不只断言 mock 调用。
- Windows 相关公开 API 保留延迟加载映射；真实 Windows GUI 回归需要 Windows 环境。
- Linux 客户端、持久转发和真实微信送达各自独立验收；离线测试不能替代它们。
- 现有服务器是已有服务常驻的 4GB 级环境。上线前需测量剩余内存和磁盘，
  不同时启动多套微信接入端或抢占现有业务资源。
